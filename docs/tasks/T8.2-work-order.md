## Hypothesis

A single-case adaptive investigation agent that maintains an explicit evidence
ledger, chooses hypotheses and tools dynamically, and retains reasoning within
one case will improve verified coverage and interprocedural accuracy over the
seven largely independent policy hunts without weakening verification.

This method hypothesis is frozen before test-set execution. Luna/max alone is
measured separately by the historical-policy effort-only control.

## Candidate method

- Exactly one benchmark case per isolated provider task; no cross-case memory.
- The model sees only the trusted clause, program scope, permitted tool
  contract, accumulated bounded observations, and its own per-case ledger.
- It may maintain, reorder, reject, or refine D1-D7 hypotheses after evidence.
- It emits exactly one `DriftPrediction`-shaped finding or one explicit
  abstention.
- The host owns instance identity and trusted clause binding.
- Every finding passes the existing policy guards and unchanged T3.4 verifier.
- No gold label, rationale, mutation data, edit history, test metric, or
  orchestration-chat transcript enters a case prompt.

## Frozen candidate budget

- semantic steps: 16;
- tool calls: 16;
- provider token accounting ceiling: 98,304;
- wall-clock ceiling: 1,200 seconds per case;
- contract repairs: unchanged from the existing shared contract;
- batch size: 1.

The observation cap, tool signatures, evidence minima, anti-shortcut policy,
D7 positive-evidence rule, static-token validator, and verifier thresholds are
unchanged.

## Development boundary

Development and prompt iteration may use unit fixtures plus frozen train/dev
rows only. Repeated Luna/max engineering trials are permitted on those
development inputs and are explicitly non-headline artifacts. Test rows and
T6-v2 evaluation labels may be used only after the method, prompt, budget,
smoke IDs, and gates are committed.

The method is not ready to freeze until a complete dev trial has zero
infrastructure/contract failures, zero unverified emissions, answer rate at
least 0.60, full-coverage F1 at least 0.70, balanced accuracy at least 0.65,
and answered accuracy at least 0.80. These are engineering readiness gates,
not publishable estimates; repeated dev use makes them optimistic.

Once the official frozen smoke begins, a method change requires a new numbered
configuration and a new predeclaration. A later configuration must use a fresh
untouched evaluation holdout if configuration 3's hidden test has already been
read.

## Gates

- Gate tests are written before implementation.
- A case cannot emit before at least one successful bounded observation.
- Ledger entries cite the observation that supports or refutes them.
- Unknown tools, malformed arguments, duplicate final answers, missing
  evidence, and exhausted budgets fail closed.
- Test fixtures prove no cross-case state and no gold-visible fields.
- The unchanged verifier is the only component that assigns a verification
  tier.
- Full offline pytest, Ruff, and `git diff --check` are green.

## Completion

T8.2 completes when the method and runner pass offline gates on the immutable
runtime-source snapshot defined by T8.1. Completion does not authorize a live
smoke; T8.3 owns live execution.
