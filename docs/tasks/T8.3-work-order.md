the current M4 release decision, and compare it with the immutable

- primary: frozen benchmark v1 test order, 196 rows;
- temporal: the separate T6-v2 add-on from T6.1, at least 20 intact pairs;
- development smoke: 14 committed development IDs, two per D1-D7 class,
  selected by a committed seed before provider execution. The frozen dev split
  contains no materializable D2 rows and no D6 rows, so those four cases are

- deterministic baselines: existing frozen Phase-5 artifacts.

No test-set pilot is permitted. The full test is run once after a valid dev
smoke and after T8.2's iterative development-readiness gates pass. Earlier

official smoke or a headline evaluation.

## Smoke validity gate

For every provider system, the 14-row dev smoke must have:

- 14/14 completed rows and exact frozen order;
- zero infrastructure failures and zero contract-rejection retries;
- exact model, reasoning, prompt, schema, tool, verifier, budget, and source
  identity;
- at least one non-null verified candidate output for the two agent systems;
  and
- no unverified emission or cross-row state.

A smoke failure stops that system. It does not authorize a prompt, budget,
verifier, threshold, or sample change. Usage-limit interruption is resumable
infrastructure state, not a method result.

## Full report

The report includes overall and local/interprocedural T1, balanced accuracy,
coverage/answered accuracy, T2 localization, T3 macro-F1, D1-D7 strata,
faithfulness by verification tier, calibration, the T6 exact interval, paired
10,000-resample intervals, a paired significance test, validity/provenance,
tokens, turns, tool calls, wall time, cache observations, and all fragile cells.

The primary paired comparison is proper agent minus RAG plus reranker on the
interprocedural stratum. Historical-policy Luna/max isolates effort effects.
Configuration 1 remains visible in the report, but a valid configuration-3
decision becomes the current release conclusion.

## Hard stop

After the frozen full run, the measured result stands. Any new method change is
configuration 4 and requires a new work order and a newly curated untouched
evaluation holdout. This is not a stop on engineering improvement: diagnosis
and further train/dev work continue until the method is useful. It is a stop on
repeatedly tuning against the same hidden test. Provider artifacts are
append/resume only by immutable run key.

## 2026-08-24 transport-qualification amendment

The first `plain_llm` request-v1 submission was intentionally launched as a
single-task transport compatibility probe before any parallel smoke execution.
The in-product Luna/max task was accepted, but its final response was a
top-level array whose items used `prediction`, `verdict`, and `loci` fields. It
does not validate against the frozen `CodexBaselineEnvelope`. The request-v1
artifact and exact final are retained under their original identities as
non-official diagnostic evidence; they must not be repaired in place,
relabelled, or counted as configuration-3 smoke output. The completed smoke
count therefore remains **0/84**.

A transport-qualification stage is now required before the official
development smoke begins. Qualification uses isolated, non-official staging
requests to prove that the in-product final can be captured and validated by
the host without changing model behavior, benchmark content, system method,
or evaluation policy. Because no valid smoke result exists, request artifacts
may be regenerated prospectively only to fix transport rendering or capture
(for example, making the required envelope unambiguous at the final response
boundary). Every regeneration must use a new request identity, preserve all
prior request/final evidence, and extend an additive freeze lineage that names
its parent and the bounded transport-only change. Once any valid official smoke
result exists, this exception closes; subsequent method or contract changes
require the normal new-configuration policy.

The in-product collaboration interface does not expose auditable provider
token usage, provider timing, provider turn telemetry, or a capability receipt
proving that tools were disabled. These fields must be recorded as
`not_recorded`; they must never be zero-filled, inferred from host behavior, or
reported as measured provider metrics. The missing tool-disable receipt is a
named validity limitation even for zero-tool baseline systems.

For `plain_llm`, `rag_dense`, `rag_reranker`, and `oracle_slice`, a qualified
task may contribute descriptive correctness and deterministic host-replay
results only when model identity, final-response identity, response-schema
identity, and every source identity are exact and all host checks pass. It may
not support provider-resource or latency comparisons. The `agent` and
`adaptive_agent` systems must not proceed beyond qualification until an
isolated staging protocol and host-owned tool logs can demonstrate exact tool
requests, outputs, ordering, authorization, and row isolation; model-authored
tool summaries are not evidence of tool execution.

The initial failure and these evidence limits are recorded in
`data/eval/legacy/m4-config3/diagnostics/plain-llm-request-v1-transport-probe.json`.
